## 0-E. Docker 部署审查（2026-11-22 续）

对 Dockerfile / 三个 compose / entrypoint / .dockerignore / 部署文档做只读审查，结论：

### 已修
- **致命（会导致容器起不来）**：`docker-entrypoint.sh` 的 `set -euo pipefail` + `grep` 空 `/app/.env` → 管道返回 1 触发退出，`TZ=auto` 或无 TZ 部署时 Node 永不启动。修复：grep 管道末尾加 `|| true`。三个 compose 默认 `TZ=Asia/Shanghai` 恰好掩盖了该 bug，但 `docker run` 不带 `-e TZ` 会中招。
- **文档与配置不符**：docs/03 的 `TZ=auto`/`DB_TZ` → 实为 `TZ=${TZ:-Asia/Shanghai}` + MySQL `--default-time-zone=+08:00`；DEPLOY.md 的 `npm ci --omit=dev` → Dockerfile 实为 `npm install --omit=dev`（刻意选择，飞牛 `npm ci` 曾 EUSAGE 退出 254，已补注释）；MySQL 镜像 `8.0` → 实际钉 `8.0.46`；"命名卷" → 实为 bind mount；`docker compose pull` 对本地 build 的 app 会失败 → 改 `pull db`。

### 有意设计（未改，已评估）

- `TRUST_PROXY=0` 默认：安全默认 + 注释明确"反代必须显式设 1"，与 server.js 一致，非缺陷。
- 权限组运行时强制：已实施（见 §0-D / 06）。

## 0-C. 第三轮：UI/动效/交互调研与落地（2026-11-22 续）

用户要求"看网站 UI、动画、交互,百度查查怎么设计"。本轮拉取业界最新指南（见 §4 来源），实际用 Playwright 截图审查了首页/找回密码弹窗/移动端，并据 Web Interface Guidelines + 动效指南做代码审查。

### 调研核心结论（对照本站）
| 原则 | 业界共识 | 本站现状 |
|---|---|---|
| 动效四功能 | 每个动画须属 feedback/continuity/hierarchy/delight，纯装饰删 | 整体克制；但正文卡片 scroll-reveal 属"用户抱怨第一名" |
| 时长 | UI 100–300ms，>500ms 显慢；进入 ease-out、退出 ease-in、进入>退出 | 多数合规（模态 0.28s），个别 0.6–0.8s 偏长 |
| 动画属性 | 只动 transform/opacity/filter/clip-path；width/margin/box-shadow/background-position 掉帧 | 有 shimmer(background-position)、l-pulse(box-shadow) 等，reduced-motion 下基本中和 |
| reduced-motion | 必须尊重，override 用 **0.01ms 不用 0**（0 跳过 end 事件挂起 JS 状态机） | 已覆盖 18 处；但 07-profile.css 与 01-variables.css 曾用 0s |
| scroll-reveal 正文 | 正文文字逐条淡入是头号动效抱怨 | motion.js 曾对 post/event/album/member/card 做 0.6s 揭示 |
| 触控热区 | ≥44×44px（Apple HIG / WCAG 2.5.8），不依赖 hover | event-edit-btn 30×30 且 hover-only |
| 设计趋势 | 紫色渐变+闪光被列为"AI 模板 cliché"；深色主题要用背景色阶重建层次而非阴影 | 本站紫色主题是品牌标识，属稳定 palette；但 hero 用 backdrop-filter 玻璃拟态，趋势已 stale |
| Core Web Vitals | LCP<2.5s / INP<200ms / CLS<0.1 | 已补 logo width/height 防 CLS；hero 用 srcset+fetchpriority 优化 |

## 1. 高优先级建议

### 1.1 把"未处理 Promise 拒绝"纳入工程防线（延续本轮 M-3）
- **依据**：Node.js 自 15 起，未处理的 Promise 拒绝默认终止进程；Express 4 **不会**把 async 路由处理器拒绝的 Promise 转给错误中间件（Express 5 才会）。本轮已修 4 处 `regenerate(async cb)`，但同类隐患可能在别处复现。[cubic: Handle Async Errors and Unhandled Rejections](https://www.cubic.dev/agents/nodejs-unhandled-promise-rejections)
- **建议**：
  1. 在 `server.js` 顶层补 `process.on('unhandledRejection', ...)` 与 `uncaughtException`，**记录后优雅退出**（由 pm2/守护拉起），而非"记日志后继续服务"——带错误状态继续跑比重启更危险。注意项目当前对连接类错误已有 `process.exit(1)` 逻辑，需避免重复/冲突。
  2. 在 `AGENTS.md`/代码评审规范里固化：Express 4 的 async handler 一律 `try/catch → next(err)`；fire-and-forget 调用必须带 `.catch()`（可记日志）。
  3. 加一条 ESLint 规则（`no-floating-promises`，需 typescript-eslint 或等价插件）或静态测试，扫描 `regenerate(async`、`forEach(async`。

### 1.2 express-rate-limit 升级与 IPv6 语义回归测试
- **依据**：上游 CVE 确认 v8.0.0–8.3.0 默认 `keyGenerator` 对 IPv4-mapped IPv6 做 /56 掩码，导致双栈服务器上所有 IPv4 客户端共享一个桶（可绕过限流），已在 8.0.2/8.1.1/8.2.2/8.3.0 修复。[NVD via Vulnerability-Lookup](https://vulnerability.circl.lu/search?vendor=express-rate-limit_project#1) · [changelog](https://github.com/express-rate-limit/express-rate-limit/blob/c416f780b7944d1e0c67ae636a1c01a2134faba2/docs/reference/changelog.mdx)
- **建议**：
  1. 确认 `server/package.json` 的 `express-rate-limit` 实际安装版本 ≥ 修复版（当前声明 `^8.6.0`，已高于修复版，风险主要在自定义 `keyGenerator` —— 本轮已修）。
  2. 把"三处自定义 keyGenerator 必须调用 `ipKeyGenerator`"写成静态守卫测试，纳入 `__tests__/security-regressions.test.js`，防止后续新增 limiter 时漏掉。
  3. 双栈部署（`APP_BIND` 含 IPv6）时，用真实 `::ffff:1.2.3.4` 形态做一次限流冒烟。

## 2. 中优先级建议

### 2.1 严格 CSP 分阶段收敛（当前 script/style 仍 unsafe-inline）
- **依据**：`06` §5 已把"CSP 内联脚本依然存在"列为已知边界；业界加固 playbook 普遍建议用 nonce/hash 逐步替换 `unsafe-inline`。[Debian/Node JS 安全实践](https://m.yisu.com/ask/31177924.html) · [Securing Express Applications 2026](https://safeguard.sh/resources/blog/securing-express-applications)
- **建议**：站点已经为 index.html 注入一次性 CSP nonce（见 `server.js`），具备收敛基础。可分步：① 先对新增脚本强制 nonce；② 把 `<style>`/内联事件处理器迁移到外链；③ 在 `Content-Security-Policy-Report-Only` 下观察一段再切强制模式。**不建议一步到位**，否则会打断主题/内联契约页。

### 2.2 WebSocket 封禁联动的"即时断连"补全
- **现状**：本轮已在握手与 `online` 心跳加封禁复核，但心跳依赖客户端周期性发消息；静默连接要等到心跳/下一次消息才被断开。
- **建议**：在封禁操作（`routes/admin_users.js` 的 ban 路由）后主动遍历 `wsService` 的 `userWsMap.get(userId)` 断开其所有连接，做到"封禁即掉线"。这是纵深防御的最后一块，改动面较小但需注入 WS 引用，故本轮未一并改。[WS 防恶意连接分层方案](https://www.volcengine.com/article/3128554)

### 2.3 依赖治理常态化
- **依据**：`npm audit` 是 Express 应用最基础的依赖防线。[Debian/Node JS 安全实践](https://m.yisu.com/ask/31177924.html)
- **建议**：把 `npm audit --audit-level=high`（`package.json` 已有 `audit` 脚本）接入 CI（`ci.yml`）与发版前检查；对 `sharp`/`mysql2`/`express` 等高危依赖订阅安全公告。注意本项目大量使用 `^` 范围版本，锁定文件 `package-lock.json` 必须随升级提交。

## 3. 低优先级 / 可选

- **死代码清理**：`public/js/birthday.js` 的 `showBirthdayEventModalNew()` 定义后无调用，且内部逻辑与 `events.js` 的 `showBirthdayEventModal()` 重叠，可择机删除（本轮仅记录未删，避免误伤）。
- **登录状态提示后移（L-1）**：登录在密码校验前返回"封禁/待审核/锁定"差异提示，构成账号状态 oracle。改成"密码校验通过后才给具体状态"可消除，但有 UX 权衡（封禁用户应知情），留待产品决策。
- **Session vs JWT 选型**：本站为同源 Web 单体 + HttpOnly Cookie + CSRF，Session 方案契合（服务端可即时强制下线、集中管控）；JWT 更适合跨端/多实例。当前单实例架构下**无需迁移 JWT**，若未来多副本再评估统一 Session 存储。[Session 与 Token 选型对比](https://www.volcengine.com/article/4144361)

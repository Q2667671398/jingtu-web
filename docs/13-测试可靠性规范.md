# 测试可靠性规范（避免脆弱测试）

> 2026-11-24 建立。起因：QA 复审指出「测试脆弱：静态源码断言主导」——
> 部分测试读源码用正则断言 `var safe = esc(` 之类代码文本，重构即坏、功能没坏也报红。

## 一、判定标准

| 类型 | 是否允许 | 说明 |
|---|---|---|
| **行为断言**（喂输入 → 断言输出/副作用） | ✅ 首选 | 重构内部实现不影响，只在行为变化时报红 |
| **契约断言**（断言 helper 的输出形状） | ✅ 允许 | 如 `ok()` 必须返回 `{success:true,...}`；改形状本就要同步改前端 |
| **反模式守卫**（断言全仓不存在某写法） | ✅ 允许 | 如「路由不得手写 `parseInt(req.query.page)`」「不得新增裸 `res.json({ok:...})`」——这类约束**只能**看源码 |
| **实现细节断言**（断言某函数名/某行代码/某正则字面量存在） | ❌ 禁止 | 这就是脆弱测试。重构就坏，但不代表功能坏 |

## 二、改造方法：让前端函数可测

前端脚本多是 IIFE，函数不导出 → 过去只能读源码断言。正确做法是**暴露一行内部引用**：

```js
// public/js/smartsearch.js 末尾
window.__smartSearchInternals = { highlight, stripTags, match };
```

测试侧用 `vm` 建最小 DOM 沙箱加载真实脚本，直接调用真实函数：

```js
const vm = require('vm');
const sandbox = { window: {}, document: stub, esc: realEsc, /* ... */ };
sandbox.window = sandbox;
vm.createContext(sandbox);
vm.runInContext(SRC, sandbox);
const { highlight } = sandbox.window.__smartSearchInternals;
expect(highlight('<img src=x>abc', 'abc')).not.toContain('<img');
```

**收益**：`smartsearch-highlight.test.js` 从 4 个源码正则断言 → 11 个行为断言，
且新增了真正的 XSS 回归保护（转义、无注入、不死循环、null 安全）。

## 三、为什么有些大文件暂时低覆盖

`chat.js`(545行) / `profile.js`(464行) / `ws_service.js`(732行) 等覆盖率 8~10%。
**不是不想测，而是硬写 mock 测试会制造脆弱测试**：

- 依赖链重：`multer` 实例、`express-rate-limit` + 自定义 `hybridStore`、`ws_service` 广播、多表事务
- mock 一旦与实现耦合（如 `secureUpload(mw)` 返回函数还是对象、`hybridStore` 是函数还是对象），
  实现一改测试就崩——**正是本规范要消除的问题**

**正确路径**（未做，记为技术债）：把路由里的纯逻辑抽成独立模块（如「群成员权限判定」
「消息可见性计算」「限流键生成」），对这些纯函数做行为测试；路由层只留薄薄的编排。

## 四、覆盖率门槛（2026-11-24 校准）

原门槛 `lines 22 / statements 20 / functions 16 / branches 10` 与实测严重脱节
（Jest 实际计算：lines 32.13 / statements 29.9 / functions 31.89 / branches 18.69），
比实测低 8~11 个百分点 → 实测回退十几个点也不会报警，**失去防回退意义**。

现校准为 `lines 32 / statements 29 / functions 31 / branches 18`（实测向下取整、留 ~1pt 余量）。

**棘轮规则**：补测提升实测值后，应同步上调门槛，只上不下。

# 五、VRChat API 调用面与封号风险评估

> 本节回答一个关键运维问题：**浏览成员页/群组页会不会打到 VRChat 官方接口、会不会被限流或封号？**
> 结论：**不会。** 绝大多数页面读取的都是本站本地数据库，VRChat 调用集中在两个受控后台任务里。

## 5.1 页面数据来源（已逐个核实代码）

| 页面/功能 | 前端请求 | 后端数据源 | 是否碰 VRChat |
|---|---|---|---|
| **成员页**（站内用户） | `/api/users/list` | `SELECT ... FROM users`（本地表） | ❌ 完全本地 |
| **群组页**（VRChat 群成员） | `/api/group/members` | `SELECT ... FROM group_roster`（本地缓存表，源码注释即标注「本地 DB」） | ❌ 完全本地 |
| 群组统计 | `/api/group/stats` | 本地 `group_roster` 聚合 | ❌ 完全本地 |
| 好友页 / 动态 / 相册 / 活动 | `/api/friends/*`、`/api/posts`… | 本地各表 | ❌ 完全本地 |
| 世界名解析 | `getCachedWorld()` | 本地 `world_cache`（24h 缓存 + single-flight） | ⚠️ 仅缓存未命中时回源，有缓存与单飞保护 |

**数据量实测**（当前库）：`users` 站内注册用户 **2 人**；`group_roster` VRChat 群成员 **475 人**。
`MEMBERS_MAX_PAGES=100`（上限 1 万）纯属**防异常 `total` 死循环的防御性常量**，与实际数据量无关。

## 5.2 真正调用 VRChat 的两处（均有系统性限流防护）

### ① 后台定时同步 —— `server/schedule.js`（系统账号）

| 项目 | 现状 |
|---|---|
| 频率 | 每 60s 一轮在线状态刷新（原 30s，因易撞 429 已放宽） |
| 覆盖策略 | **游标轮转**：小群（≤80 人）每轮全员；大群分批推进持久游标，长期覆盖全员 |
| 并发保护 | `onlineRefreshInFlight` 互斥，上轮未完则跳过，绝不重叠 |
| 配额让路 | 令牌桶已有排队（多为用户交互请求）时本周期直接放弃 |
| 单轮请求上限 | 好友翻页 ≤20 页 + 非好友回退压到 **12** + 信任补充 ≤20 ≈ 最坏 32 req/轮 |
| 数据源优先级 | 群友共享态（好友视角，最准）→ 系统账号好友 → 非好友公开回退 |

### ② 群友互助上报 —— `/api/group/presence/contribute`（用户自己的 VRChat cookie）

| 项目 | 现状 |
|---|---|
| 触发 | 打开群组页时 + 全局每 10 分钟一次 |
| 节流 | 前端 `_lastPresenceContribute` **5 分钟**内不重复；全局定时器 10 分钟 |
| 后台保护 | `if (document.hidden) return;` 页面隐藏即跳过，不浪费配额 |
| 服务端模式 | 已改为 **onlineOnly 快模式**（只拉在线好友），实际耗时降到秒级 |
| 设计意图 | **有意把配额分摊到多个用户账号**，避免系统账号单点撞 429 |

## 5.3 限流防护机制（`server/vrc.js`）

| 机制 | 实现 |
|---|---|
| **全局令牌桶** | 全站对 VRChat 请求 **≤40 req/min**（官方约 50，留 20% 余量） |
| **429 指数退避** | 连续 429 递增惩罚：第 1 次罚 12 令牌（≈18s），第 2 次 24（≈36s），自我降温；成功后清零 |
| **透明重试** | 429 时退避重试最多 3 次，不冒泡成业务错误 |
| **请求收敛** | 世界名走 24h 缓存 + single-flight；群成员状态走批量解析（非逐个查询） |

## 5.4 封号风险判断

| 维度 | 评估 |
|---|---|
| 是否存在**写操作**打到 VRChat？ | **无**。所有对 VRChat 的调用都是只读（好友列表、用户资料、世界信息） |
| 是否会高频匿名扫描？ | **否**。全部经登录态 cookie，且受 40/min 令牌桶约束 |
| 单账号是否单点超限？ | **否**。定时任务有 inFlight 互斥 + 配额让路；群友互助把负载分摊到多账号 |
| 429 处理是否正确？ | **是**。递增惩罚 + 退避重试，不会因重试加剧风控 |
| 综合风险 | **低**。但需注意：VRChat 未公开封号/限流的确切阈值，属于「按最佳实践规避」而非「官方担保」 |

## 5.5 运维建议（有风险时才需要动）

1. **不要缩短** `schedule.js` 的 60s 刷新周期 —— 注释已记录 30s 会撞 429
2. **不要提高** 令牌桶 `40/min` 上限 —— 已按官方 50/min 留 20% 余量
3. 新增任何调用 VRChat 的功能，**必须**走 `vrcRequest()` 统一入口（自动获得令牌桶与 429 退避），禁止裸 `fetch` 打 `api.vrchat.cloud`
4. 若未来注册用户大幅增长，`contributePresence` 的 5 分钟节流**应保留**（用户越多分摊越充分，但也要防单个高频用户）
